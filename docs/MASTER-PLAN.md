# FS Internal System — Full Feature Build Plan

## Context

`fs-internal-system` (at `/usr/share/nginx/html/fs-internal-system`) is a fresh scaffold: Vite + React 19 + TS frontend, Capacitor 8 (iOS/Android), and a `server/` backend (Node 22 ESM, Express 5 + Socket.IO + mysql2, Dockerized for future AWS ECS). The user wants it built into an internal ops platform for their company with:

1. **Auth & accounts** — email+password; self-registration limited to admin-configurable allowed email domains (e.g. flowerstore.ph, potico.ph, potico.co.th); roles: **admin + member**
2. **Slack-style messaging** — public/private channels, DMs, history, real-time, unread counts
3. **Projects** — members, markdown documentation pages, kanban task board (drag & drop, assignees, due dates, comments)
4. **File/image sharing** — attachments on messages/tasks/docs; local disk in dev, S3 in prod
5. **Push notifications** — FCM/APNs via `@capacitor/push-notifications`
6. **Teleconference (Google Meet-style)** — video/audio calls via **self-hosted LiveKit** (Apache-2.0 WebRTC SFU — rooms, simulcast, screen share all confirmed free in OSS). **Deployment correction (verified against docs.livekit.io): ECS is not a documented LiveKit target and Docker deploys want host networking — production runs on an EC2 VM via LiveKit's official cloud-init + Caddy path (or K8s w/ host networking later), alongside (not on) the ECS services.** Calls startable from any channel (Slack-huddle style) plus ad-hoc meeting rooms
7. **Departments** — org units (e.g. Marketing) that own channels and projects; department members auto-join their department's channels; other staff can browse/join **public** department channels
8. **Strict privacy rule** — private channels, private projects, and department-private groups are **completely invisible** to non-members: excluded from channel/project lists, search, and socket rooms; API returns 404 (not 403) for private resources the requester doesn't belong to, so existence isn't leaked. Admins retain visibility for governance.
9. **AI support channels (ticket-through-chat)** — a second channel *kind*: `support`. Each support channel is bound to a target project + intake kanban column. When someone chats there, an AI assistant (Claude API) reads the conversation, asks clarifying questions as a bot user when needed, then files a ticket — a task created in the bound project's intake column with an AI-written title/summary/priority, linked back to the originating messages — and posts a confirmation with the ticket link. The whole mechanism rides on a generic **automation event bus** so future automations (digests, alerts, other bots) plug in the same way.
10. **AI-exposed API** — the platform's own API is consumable by AI agents (not just the built-in intake bot): scoped **service tokens** let an AI create/update tickets, change ticket status (move between columns), post/read chat messages, and read/write documentation. Also exposed as an **MCP server** (Streamable HTTP endpoint on the same backend) so Claude or any MCP-capable agent can operate the system with typed tools. Admin UI manages tokens + scopes.
11. **Office support — own Sheets + previews** — (a) **Native Sheets**: a first-class project doc type built on **Univer** (Apache-2.0 embedded spreadsheet engine), stored structured in our DB under the same visibility rules as markdown docs; v1 concurrency = lock-based single editor (socket-held lock, others view live), real co-editing later if needed. xlsx import/export via SheetJS. **Required native capabilities (acceptance criteria)**: Excel-compatible formula engine (SUM/VLOOKUP/INDEX/MATCH/IF, text/date/statistical functions, cross-sheet refs), conditional formatting, data validation, filters/sort, merge/freeze — all core OSS Univer plugins, wire them all in. **Macros** = JS scripting on Univer's **Facade API (`univerAPI`)** — the verified official programmatic surface (returned by `createUniver()`; snapshot round-trip = `createWorkbook(snapshot)` / `fWorkbook.save()`); the Uniscript plugin (alive, publishes in lockstep) is just an in-UI panel over that same Facade API and can be mounted as the user-facing macro editor. Plus AI/API-driven manipulation through Phase 8 `write_sheet`. VBA from imported .xlsm does not run (true of every web spreadsheet incl. Google/OnlyOffice — data + formulas survive import, VBA stripped; surface a notice on import). Known OSS gaps (verified against Univer v0.25.x, 2026-07-22): pivot tables, charts, sparklines, xlsx import/export, and co-editing are Pro/paid — our design already routes around the latter two (SheetJS for xlsx, lock-based editing), and pivot/charts get flagged to the user if requested later (options: buy plugin or OnlyOffice fallback). Formula engine (incl. VLOOKUP/XLOOKUP/INDEX/MATCH, cross-sheet refs), conditional formatting, data validation, filters/sort, merge/freeze all confirmed OSS. Setup via `@univerjs/presets` (`@univerjs/preset-sheets-core`), mounted in React with a `useEffect` + container ref (no official React wrapper exists). (b) **Uploaded office files** (docx/xlsx/pptx/ODF/CSV/PDF attachments): **view-only in-app previews** — SheetJS renders xlsx/csv, mammoth renders docx, PDFs natively; no extra container. **SheetJS install (security-critical, verified): the npm `xlsx` package is frozen at 0.18.5 with two unpatched CVEs (CVE-2023-30533 prototype pollution, CVE-2024-22363 ReDoS); install the official 0.20.3 tarball from cdn.sheetjs.com, vendor it in the repo, and add a package.json `overrides` entry so no transitive dependency pulls the vulnerable npm version.** **Deferred**: OnlyOffice Document Server remains the documented option if full-fidelity *editing of uploaded* Office files ever becomes a real need.

12. **Script editor (Python)** — an Automations → Scripts area with an in-app code editor (CodeMirror 6, Python syntax) where staff write scripts that automate the platform (bulk ticket ops, sheet crunching, report generation). Execution is **server-side in a sandboxed runner**: a separate minimal container (python:3.12-slim based) that consumes a job queue, runs each script as a non-root child process with hard timeout/memory caps and **no network egress except the internal API**, into which each run receives a short-lived scoped service token (the Phase 8 mechanism) as env vars plus a small `fs_sdk` Python helper (thin requests wrapper over the REST API). stdout/stderr + exit status captured per run, shown in a run-log panel. Admin-controllable who may create/run scripts (default: admin-only to start). JavaScript as a second language later if wanted.
13. **AI Routines (Claude Code-style)** — scheduled agent tasks: user defines a routine as a natural-language prompt + cron schedule (+ optional target channel for output). On schedule, the backend runs an agentic loop against the **Claude API** (`@anthropic-ai/sdk`, tool-use loop) giving the model the Phase 8 MCP toolset (tickets/chat/docs/sheets — same scopes, same bot-identity audit trail), capped iterations + token budget per run. Examples: "every weekday 8am post yesterday's new tickets summary to #support", "weekly: scan stale in-progress tasks and nudge assignees". UI mirrors Claude Code's routines: list w/ enable/disable + "Run now", per-run history with a readable transcript (tool calls + results), failure alerts to the owner via DM.

14. **Google Calendar + Gmail integration** — per-user Google OAuth connection ("Connect Google" in /settings; auth-code flow, offline access, encrypted refresh tokens at rest). **Calendar**: /calendar agenda view of the user's upcoming events; create events from the app (channel header "Schedule meeting" → event whose description carries the LiveKit call link; task detail "Add to calendar" for due dates); event reminders DM'd by the bot. **Gmail**: per-user inbox panel (recent/unread, read a message, compose/send as yourself); plus an **org-level support mailbox connector** (admin connects e.g. support@flowerstore.ph): poller ingests new inbound emails into a designated support channel as messages, where the existing Phase 7 AI intake turns them into tickets — email becomes a ticket source for free. **AI tools**: `list_calendar_events`, `create_calendar_event`, `search_gmail`, `send_gmail` (send = per-user tokens only, never the org mailbox) added to MCP/routines so routines like "every morning DM me today's meetings + unread ticket emails" work. If the company is on Google Workspace, mark the OAuth app Internal to skip Google's verification review.

15. **File management connected to Google Drive** — three layers on top of the Phase 12 Google connection: (a) **Project Files tab**: each project can bind a Drive folder; the tab browses it in-app (folder tree, search, metadata), uploads from the app into the folder, and opens Docs/Sheets/Slides in their native Google editors in a new tab — Drive stays the source of truth for heavyweight files, our native sheets/docs remain the in-app collaborative layer; (b) **Attach from Drive**: Google Picker in the chat composer and task detail — attaches a Drive file as a rich chip (name, icon, owner, open link) without duplicating the bytes; (c) **My Drive browser**: personal Drive search/browse panel beside the existing uploads. Attachments table gains a `provider` discriminator (`internal` = our disk/S3 storage vs `gdrive` = reference to a Drive file) so both kinds render uniformly in chat/tasks/docs. AI tools `search_drive`/`list_drive_files` added for routines ("find last month's inventory sheet"). Known caveat (documented in UI): Drive enforces its own permissions — an attached Drive file may still require the viewer to request access in Google; optional per-attach "share with domain" toggle mitigates when scopes allow.

16. **Personal notes** — a private "Notes" space per user (like Slack's jot-it-down DM-to-self, but first-class): markdown notes with title, pin-to-top, and search; visible ONLY to their owner (not even admins — personal scratch space, stated in UI). Reuses the Phase 3 markdown editor + sanitized renderer wholesale. Sidebar "Notes" entry above DMs. Deliberate v1 limits: no attachments, no sharing (a note you want to share becomes a project doc — one-click "Convert to project doc" action), and no AI/MCP access to notes v1 (personal data stays out of agent reach; revisit only with explicit per-user opt-in).

**UI direction: copy Slack's UX.** Replicate Slack's layout and interactions (not its assets/branding): dark aubergine left sidebar — workspace name + search top; collapsible sections for each Department, Channels, DMs; `#` prefixes, unread bolding + badge counts; white content pane with channel header (topic, member count, huddle/call button), hover-action message rows (edit/delete/react placement), composer with attach + @mention popover at bottom, right-hand detail drawer (task detail, profile, call participants). Keyboard: Ctrl+K quick-switcher. shadcn/ui + Tailwind themed to match Slack's visual language.

Existing code to build on: `server/src/index.ts` (basic channels/messages REST + socket events — currently **unauthenticated, trusts client userId**; must be fixed in Phase 1), `server/schema.sql` (users/channels/channel_members/messages), `src/lib/socket.ts` client helper. PM2 serves locally (static :3000, API :4000).

## Stack decisions

- **Backend ORM**: **Drizzle ORM** on the existing mysql2 pool (project will grow — user decision). Schema lives in TypeScript (`server/src/db/schema.ts`, split per domain: auth.ts, chat.ts, projects.ts, files.ts, push.ts, departments.ts, calls.ts), giving end-to-end types from DB to API. `drizzle-kit generate` produces versioned SQL migrations (`server/drizzle/`), `drizzle-kit migrate` applies them (dialect 'mysql'; note MySQL has no transactional DDL — failed migrations leave partial state, so test on a scratch DB first) — replaces both the existing hand-written `schema.sql` and any custom runner (baseline migration 000 recreates the current users/channels/channel_members/messages tables). Docs-recommended install line is `drizzle-orm@rc` (v1.0-rc); pin deliberately. **Verified caveat (2026-07-22): MariaDB is NOT officially supported by Drizzle** (relational query builder emits `LEFT JOIN LATERAL`, unsupported on MariaDB) → **local dev DB = MySQL 8 Docker container, not the system MariaDB** — also eliminates the dev/prod RDS-MySQL drift risk. Chosen over Prisma: no codegen binary/engine in the alpine Docker image, SQL-like query builder keeps the complex visibility queries explicit, and raw SQL escape hatch (`sql``) for hot paths like unread counts. Add: `drizzle-orm`, `drizzle-kit` (dev), **`jose`** (JWT — ESM-native, actively maintained; verified advised over stale CJS `jsonwebtoken` for new projects), `argon2` (alpine/musl prebuilds verified — no build toolchain needed on node:22-alpine), `zod`, **`multer` ^2.2.0 (security floor 2.1.0 — five 2025–2026 CVEs in earlier lines)**, `@aws-sdk/client-s3` + presigner, `express-rate-limit`, **`memcache` (jaredwray)** for memcached (verified: `memjs` unmaintained since early 2024), `firebase-admin` v14 (Phase 5; `sendEachForMulticast` confirmed current). Express 5 confirmed GA (async error propagation built in).
- **Frontend**: **react-router v8** (verified current major since 2026-06; library mode `createBrowserRouter` fully supported; ESM-only, Node 22+, import from `react-router` — no `react-router-dom`), TanStack Query v5, Tailwind v4 + shadcn/ui (verified: `@tailwindcss/vite` + `@import "tailwindcss"` + `npx shadcn@latest init`), **`@atlaskit/pragmatic-drag-and-drop`** for kanban DnD (verified: dnd-kit stable packages stale since Dec 2024; Atlassian's is actively maintained, powers Trello/Jira, headless — we own the a11y layer), zustand v5, react-markdown + remark-gfm + **rehype-sanitize** (stored-XSS defense). Capacitor plugins: `@capacitor/preferences`, `@capacitor/push-notifications`, `@capacitor/app`, `@capacitor/browser`.
- **Auth = JWT, not cookies**: Capacitor webview origins (`capacitor://localhost`) make cookies unreliable/cross-site; Bearer tokens work identically in browser, webview, and Socket.IO `auth` payload. Access JWT 15 min (HS256 via `jose`, claims sub/role) in memory; opaque refresh token 30 days stored sha256-hashed w/ rotation + family reuse-detection; persisted via `@capacitor/preferences` (native) / localStorage (web) behind one `storage.ts` abstraction. `api.ts` wrapper: on 401 → single-flight refresh → retry once.
- **Testing (TDD per superpowers)**: **Vitest** for service/unit tests (visibility fragments, token service, task-move positions get tests FIRST), **supertest** for route/integration tests against a scratch MySQL 8 container, **Playwright** for E2E flows (login, two-context chat realtime, kanban drag, private-channel invisibility). Each phase's verify list becomes automated tests where feasible; manual checks reserved for device/ops items. CI-ready: `npm test` green is part of every phase's exit criteria.
- **Execution methodology**: this document is the master spec. At the start of each phase, write a superpowers-style task-level plan (exact files, failing test first, small frequent commits) and execute task-by-task; the phase's "Verify" list is its acceptance gate.
- **Ops baseline**: structured logging via `pino` from Phase 0 (request-id middleware; pretty in dev, JSON in prod); DB backups = nightly `mysqldump` locally / RDS automated snapshots in prod; frontend prod hosting decision deferred but noted — static `dist/` goes to S3+CloudFront when the backend moves to ECS (PM2 static serving is the local/dev story only).

## Database (Drizzle schema, migrations 000–014, MySQL 8)

All tables below are defined as Drizzle TS schema; the numbered groupings map to `drizzle-kit generate` runs per phase. 000 = baseline of the existing four tables. Dev + prod are both MySQL 8+ (local Docker container / prod confirmed MySQL 8+ by user 2026-07-22) — no dialect drift.

- **001 auth**: users + `password_hash`, `role ENUM('admin','member')`, `avatar_url`, `is_active`; `settings` (key/JSON value — `allowed_domains`); `refresh_tokens` (token_hash, family_id, expires/revoked).
- **002 messaging**: channels + `type ENUM('public','private','dm')`, `topic`, `dm_key` (unique `dm:<minId>:<maxId>` for DM dedup), name nullable; channel_members + `role`, `last_read_message_id` (unread counts); messages + `edited_at`, `deleted_at`, index `(channel_id, id)` for cursor pagination, **FULLTEXT index on body (message search)**; `message_mentions`; **`message_reactions` (message_id, user_id, emoji VARCHAR(32), PRIMARY KEY (message_id, user_id, emoji), INDEX (message_id))** — the Slack-UI hover "react" action needs it.
- **003 projects**: `projects`, `project_members (role lead|member)`, `docs` (markdown MEDIUMTEXT), `task_columns` (position INT), `tasks` (column_id, assignee_id, due_date, `position DOUBLE` midpoint ordering, index `(column_id, position)`), `task_comments`; **`notes` (id, user_id, title VARCHAR(200), content MEDIUMTEXT — markdown, pinned BOOL DEFAULT FALSE, created_at, updated_at, INDEX (user_id, pinned, updated_at), FULLTEXT (title, content))** — owner-only personal notes.
- **004 files**: `attachments` (uploader, nullable message_id/task_id/doc_id, storage_key, mime, size; unlinked rows >24h GC'd).
- **005 push**: `device_tokens` (user_id, token, platform, last_seen_at).
- **006 departments** (created in Phase 1 with admin CRUD; scoping applied in Phases 2–3): `departments` (id, name, description); `department_members` (department_id, user_id, role ENUM('lead','member')); channels + `department_id BIGINT NULL` and projects + `department_id BIGINT NULL` (NULL = org-wide). Joining a department auto-inserts channel_members rows for that department's channels (service-layer, also backfills when a channel is later created under the department).
- **007 calls** (Phase 6): `calls` (id, channel_id NULL for ad-hoc, room_name UNIQUE, started_by, started_at, ended_at NULL) — history + "call in progress" indicator.
- **008 support/AI** (Phase 7): channels + `kind ENUM('standard','support') DEFAULT 'standard'`; `support_configs` (channel_id UNIQUE, project_id, intake_column_id, ai_enabled BOOL, instructions TEXT NULL — extra steering prompt per channel); tasks + `origin_channel_id NULL`, `origin_message_id NULL`, `source ENUM('manual','support') DEFAULT 'manual'`, `priority ENUM('low','medium','high','urgent') NULL`; users + `is_bot BOOL DEFAULT FALSE` (seeded "FS Assistant" bot account authors AI messages).
  Forward-compat note: `kind` (behavior) is deliberately separate from `type` (visibility) so future kinds (announcements, integrations) don't multiply enums.
- **009 AI/service tokens** (Phase 8): `api_tokens` (id, name, token_hash CHAR(64) UNIQUE, scopes JSON — e.g. ["tickets:write","chat:write","docs:read"], acts_as_user_id → a bot user, created_by, last_used_at, expires_at NULL, revoked_at NULL). Every AI-made ticket/message/doc edit is attributed to the token's bot user for a clean audit trail.
- **010 sheets** (Phase 9): `sheets` (id, project_id, title, data LONGTEXT — Univer workbook snapshot JSON, created_by, updated_by, updated_at, INDEX (project_id)); `sheet_locks` handled in-memory via presence service (socket-held edit lock, auto-release on disconnect) — no table needed. Docs list UI shows markdown docs and sheets together (type icon differentiates).
- **011 scripts** (Phase 10): `scripts` (id, project_id NULL — NULL = org-wide, name, language ENUM('python') — extensible, source MEDIUMTEXT, token_scopes JSON, enabled, created_by, updated_at); `script_runs` (id, script_id, status ENUM('queued','running','succeeded','failed','timeout'), triggered_by, stdout MEDIUMTEXT, stderr MEDIUMTEXT, exit_code, started_at, finished_at, INDEX (script_id, started_at)) — `script_runs` doubles as the job queue (runner polls status='queued').
- **012 routines** (Phase 11): `routines` (id, name, prompt TEXT, cron VARCHAR(60), timezone, enabled, tool_scopes JSON, output_channel_id NULL, owner_id, last_run_at, created_at); `routine_runs` (id, routine_id, status ENUM('running','succeeded','failed','budget_exceeded'), transcript JSON — ordered tool calls/results/text, tokens_used, started_at, finished_at, INDEX (routine_id, started_at)).
- **013 google** (Phase 12): `google_accounts` (id, user_id NULL — NULL = org-level connector, kind ENUM('user','support_mailbox'), google_email, refresh_token_enc VARBINARY(1024) — AES-256-GCM w/ env key, scopes JSON, connected_by, connected_at, UNIQUE(user_id, kind)); `gmail_ingest_state` (google_account_id UNIQUE, history_id/last_internal_date watermark, target_channel_id) for the support-mailbox poller (idempotent ingest, no dupes); ingested emails become messages authored by the bot with `origin_email_msgid` stored in a small `message_email_origins` table (message_id UNIQUE, gmail_message_id, from_addr, subject) so replies/threading stay traceable.
- **014 drive** (Phase 13): `project_drive_folders` (project_id UNIQUE, folder_id, folder_name, connected_by, connected_at); attachments + `provider ENUM('internal','gdrive') DEFAULT 'internal'`, `drive_file_id VARCHAR(120) NULL`, `web_view_link VARCHAR(500) NULL`, `icon_mime VARCHAR(120) NULL` (storage_key becomes NULL-able, exactly one of storage_key/drive_file_id set per row).

**Visibility rules (enforced in every list/get query + socket join):** a user sees a channel/project if it is public (org-wide or department-public), OR they are a member, OR they belong to the owning department. Private + non-member → excluded from lists and 404 on direct access. Admin role bypasses for governance. Centralize as SQL fragments in `channelService`/`projectService` (single source of truth) rather than scattering WHERE clauses.

## API surface (all `/api`, Bearer auth except /auth/*)

- **Auth**: POST register (domain-checked) / login / refresh (rotating; reuse revokes family) / logout; GET me
- **Admin** (requireAdmin): GET/PUT settings allowed_domains; GET users; PATCH users/:id (role, isActive)
- **Users**: GET /users (directory); PATCH /users/me
- **Chat**: GET /channels (w/ unread counts); POST /channels; GET/PATCH /channels/:id; members add/remove; GET /channels/:id/messages?before=<id>&limit=50; POST /channels/:id/read; POST /dms (find-or-create via dm_key); PATCH/DELETE /messages/:id (own, soft delete); **PUT/DELETE /messages/:id/reactions { emoji }** (socket `message:reaction` broadcast); **GET /search/messages?q&channelId?** — FULLTEXT search filtered through the centralized visibility fragments (private content of non-members never surfaces); channel/user search for the Ctrl+K quick-switcher is client-side over the already-visible list
- **Projects**: CRUD /projects, members; GET/POST /projects/:id/docs, GET/PATCH/DELETE /docs/:id; GET /projects/:id/board (columns+tasks single payload); columns CRUD; tasks CRUD; **POST /tasks/:id/move { columnId, beforeTaskId?, afterTaskId? }** — server computes midpoint position (authoritative)
- **Notes (owner-only, hard-scoped `WHERE user_id = req.auth.userId` in every query)**: GET /notes?q&pinned (FULLTEXT search within own notes only); POST /notes; GET/PATCH/DELETE /notes/:id (404 for anyone else's — including admins); POST /notes/:id/convert-to-doc { projectId } (creates a project doc from the note, then deletes the note). Service tokens: NO notes scope exists — notes endpoints reject token auth outright (personal data stays out of agent reach).
- **Files**: POST /uploads (multipart, mime whitelist, 20MB cap) → unlinked attachment rows; GET /files/:id (membership check — **404 for non-members, consistent with the platform privacy rule** → dev stream / prod 302 presigned S3, 60s); signed URLs embedded in message payloads for `<img>`
- **Push**: POST/DELETE /push/tokens
- **Departments**: GET /departments (all — they're org structure); POST /departments (admin); PATCH/DELETE /departments/:id (admin); POST/DELETE /departments/:id/members (admin or dept lead) — join triggers auto-membership of dept channels
- **Calls (LiveKit)**: POST /api/calls { channelId? } → creates/reuses active call row + returns LiveKit access token (minted with `livekit-server-sdk`, identity/name from JWT, room grant only — membership checked against channel visibility first); POST /api/calls/:id/end; GET /api/channels/:id/call (active call, for "join call" banner). LiveKit server itself is a separate container; API keys via env.
- **Support channels**: POST /channels accepts `kind: 'support'` + `supportConfig { projectId, intakeColumnId, instructions? }` (creator must be member/lead of target project); GET/PUT /api/channels/:id/support-config; tickets themselves are ordinary tasks (existing task endpoints) carrying `source: 'support'` + origin links, so the kanban board shows them with a "from #channel" chip linking back to the conversation.
- **AI/service access**: no separate endpoint namespace — the existing REST surface accepts service tokens (`Authorization: Bearer fsk_<random>`) via the same auth middleware; `req.auth` = { kind: 'user' | 'token', userId (bot identity for tokens), scopes }. Scope map: `tickets:read/write` → tasks + move/status + comments; `chat:read/write` → channels/messages (visibility rules apply to the bot user's memberships); `docs:read/write` → project docs. Admin token management: GET/POST /api/admin/tokens, DELETE /api/admin/tokens/:id (revoke); plaintext key shown once at creation.
- **MCP server**: `POST /mcp` (Streamable HTTP — verified current recommended transport; `@modelcontextprotocol/sdk` 1.x (`McpServer` + `StreamableHTTPServerTransport`); note SDK v2 split packages `@modelcontextprotocol/server`/`client` reach stable ~2026-07-28 — build on 1.x now, keep the MCP layer thin for an easy v2 migration; auth = service token) exposing typed tools over the same services: `create_ticket`, `update_ticket`, `move_ticket_status`, `list_tickets`, `search_messages`, `post_message`, `list_channels`, `read_doc`, `write_doc`, `list_docs`. Thin wrappers — no business logic in the MCP layer.
- **Sheets**: GET/POST /api/projects/:id/sheets; GET/PATCH/DELETE /api/sheets/:id (PATCH saves workbook snapshot — requires holding the edit lock); POST /api/sheets/:id/import (xlsx via SheetJS) / GET /api/sheets/:id/export (xlsx). Socket: `sheet:lock:acquire/release` + `sheet:updated { sheetId }` (viewers refetch). `sheets:read/write` added to service-token scopes + MCP tools (`read_sheet`, `write_sheet`) so AI can work with sheets too.
- **Office previews**: client-side rendering of attachments — SheetJS (xlsx/csv), mammoth (docx), native PDF; server just streams the file (existing GET /api/files/:id).
- **Scripts**: GET/POST /api/scripts; GET/PATCH/DELETE /api/scripts/:id; POST /api/scripts/:id/run → creates queued script_run; GET /api/scripts/:id/runs + GET /api/script-runs/:id (status + logs, poll or `script:run:update` socket event). **Runner-facing endpoints (runner-scope service token only): POST /api/script-runs/claim (atomically claims oldest queued run — `UPDATE ... WHERE status='queued' ORDER BY id LIMIT 1` returning source + per-run child token) and POST /api/script-runs/:id/complete { status, stdout, stderr, exitCode }.** Per-run child tokens minted with the script's `token_scopes` and ~15 min expiry.
- **Routines**: GET/POST /api/routines; GET/PATCH/DELETE /api/routines/:id (enable/disable via PATCH); POST /api/routines/:id/run-now; GET /api/routines/:id/runs + GET /api/routine-runs/:id (transcript). Scheduler = `croner` in the API process (single-task; revisit if multi-task). Each run = Claude tool-use loop over in-process service functions (same implementations the MCP server wraps — no HTTP round-trip to itself), max ~15 iterations, per-run token budget from env, failures DM the owner.
- **Google**: GET /api/google/auth-url (state=user or support_mailbox[admin]); GET /api/google/callback (code exchange, encrypt + store refresh token); DELETE /api/google/connection (revoke + delete); GET /api/google/status. Calendar: GET /api/calendar/events?from&to; POST /api/calendar/events { title, start, end, attendees?, description? }. Gmail (per-user): GET /api/gmail/messages?q&label; GET /api/gmail/messages/:id; POST /api/gmail/send { to, subject, body }. Admin: PUT /api/admin/google/support-mailbox { targetChannelId } (start/stop poller). `googleapis` npm client; `googleService.ts` centralizes token refresh (auto-refresh, mark connection broken on invalid_grant and DM the owner to reconnect). Scopes requested: `calendar.events`, `gmail.readonly` + `gmail.send` (user), `gmail.readonly` (support mailbox). Capacitor: OAuth runs in the system browser (`@capacitor/browser`) with deep-link return; web uses a popup/redirect.

## Socket events

Connect with `auth: { token }`; `io.use` JWT middleware sets `socket.data.userId`, auto-joins `user:<id>` + all membership `channel:<id>` rooms.
- C→S: `channel:join`/`leave` (membership-verified), `message:send { channelId, body, attachmentIds? }` + ack (**userId from socket.data, never payload**), `typing:start/stop`
- S→C: `message:new/updated/deleted`, `typing`, `channel:created`, `call:started` / `call:ended` { channelId, callId } (drives "join call" banner + sidebar indicator), (P3 nice-to-have) `board:changed { projectId }` → client invalidates board query
- Scale-out readiness: all emits via `io.to(room)`; presence isolated in `services/presence.ts`. Single backend task initially — if scaled to multiple tasks later, Socket.IO needs a pub/sub adapter at that point (memcached cannot fill this role — no pub/sub; decision deferred, nothing depends on it now).

**Automation event bus (extensibility backbone):** `services/events.ts` — tiny typed in-process emitter; `messageService.create` publishes `message.created { message, channel }` after commit + socket broadcast. Automations register as subscribers in `server/src/automations/` (first: `supportIntake.ts`). Async, fire-and-forget with error isolation (a failing automation never breaks message send). This is what makes ticket-through-chat and future bots pluggable rather than hard-wired into chat handlers.

**AI intake flow (supportIntake automation):** on `message.created` in a `kind='support'` channel with `ai_enabled` → skip if author is bot → load last ~20 messages of context + support_config.instructions → call **Claude API** (`@anthropic-ai/sdk`, model via env `AI_MODEL`, default `claude-sonnet-5`; structured tool-use output) → model returns one of: `ask_clarification { question }` (bot posts question in channel) or `create_ticket { title, description, priority }` → server creates the task in the bound project/intake column (source='support', origin links), posts bot confirmation message with ticket link. Debounce per channel (5s) so rapid consecutive messages produce one AI turn; hard cap on tokens; `ANTHROPIC_API_KEY` via env/Secrets Manager. Bot messages flow through normal message pipeline (visible via sockets, no automation re-trigger thanks to is_bot guard).

**Caching layer: memcached** (user decision) — `memcache` (jaredwray) client behind a small `cache.ts` wrapper (get/set/del with TTL, namespaced keys). Local dev: memcached via Docker or skip (wrapper no-ops when `MEMCACHED_SERVERS` unset). Prod: ElastiCache Memcached. Used for: channel-list + unread-count payloads (invalidate on message/read events), settings (`allowed_domains`), rate-limit counters. Introduced in Phase 2 where the hot queries appear.

## Cross-phase risks

1. Capacitor webview auth — prove in Phase 1 before building on it.
2. Existing unauthed socket events must be locked down in Phase 1 or messaging ships insecure.
3. Reverse-infinite-scroll message list — most iteration-heavy UI.
4. **MariaDB vs MySQL 8 drift — REOPENED by user directive (2026-07-22): local dev runs on the system MariaDB (no local MySQL install available), prod remains MySQL 8+.** This is safe in practice because the codebase only uses Drizzle's core query builder (`db.select/insert/update/delete`), never the relational query API (`db.query.*`) that emits the MariaDB-incompatible `LEFT JOIN LATERAL` — enforce this as a standing rule in code review. Also: MySQL/MariaDB have no transactional DDL — always dry-run migrations on a scratch DB. The MySQL 8 Docker container and docker-compose.yml from Phase 0 were removed as no longer needed for local dev; re-add only if a genuine MySQL-8-only feature is needed before an RDS deploy for parity testing.
5. Scale-out later: ALB sticky sessions required; multi-task Socket.IO will need a pub/sub adapter (not memcached — it has no pub/sub); room/presence discipline keeps this a drop-in decision for later. Memcached covers caching only.
6. iOS push needs Apple Developer account + physical device.
7. Privacy leaks are the top correctness risk with departments in play: every new list endpoint must reuse the centralized visibility SQL fragments; verify with a dedicated non-member test account each phase.
8. LiveKit infra (verified): not an ECS-documented workload — plan an EC2 VM (official cloud-init/Caddy path) with direct UDP media ports; also, Capacitor webviews are outside LiveKit's supported browser matrix, so device testing happens at Phase 6 START, with native/RN SDKs as the documented fallback. Keep everything else independent of this phase.
9. Service tokens are powerful credentials: hash at rest, show plaintext once, scope-check on every route (not just at the router edge), and route all AI writes through bot identities so humans can audit what an agent did.
10. Univer bundle weight and API churn (pre-1.0-style releases) — pin versions, lazy-load the route, and keep the workbook snapshot JSON as the storage contract so the editor can be swapped without a data migration. OnlyOffice remains the documented fallback if uploaded-file *editing* fidelity is ever required.
11. The script runner is arbitrary-code-execution **by design** — it is the platform's biggest attack surface. Non-negotiables: separate container (never exec in the API process), non-root, timeout + memory caps, egress blocked except the API, short-lived minimal-scope tokens, admin-only script creation until there's reason to widen it. Review this phase's code with a security pass before deploy.
12. AI routines burn tokens on a schedule — per-run budget + monthly cap env vars, and the transcript UI keeps spend visible. A runaway cron (every-minute routine left enabled) is the likeliest cost accident; consider minimum interval guard (e.g. 5 min) except for admins.
13. Google refresh tokens are long-lived credentials to real mailboxes — encrypt at rest (key via Secrets Manager, never in the repo), request minimum scopes, `send_gmail` only ever uses the acting user's own token, and the AI never gets org-mailbox send. Verified scope classes: `gmail.readonly` is RESTRICTED (CASA assessment for external apps), `gmail.send` is sensitive, `drive.file` + Picker is non-sensitive; a Google Workspace **Internal** app skips verification entirely including restricted scopes — confirm Workspace status before Phase 12; otherwise external testing mode = 100-user cap + 7-day refresh-token expiry.
