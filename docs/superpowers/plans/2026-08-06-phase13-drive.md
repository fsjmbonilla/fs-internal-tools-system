# Phase 13: Drive file management

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal (master plan §Phase 13):** Google Drive as the heavyweight-file layer:
each project can bind a Drive folder and browse it in-app, anyone can attach a
Drive file to chat/tasks as a reference chip (no byte duplication), a personal
My Drive panel sits beside uploads, and agents get `search_drive` /
`list_drive_files`.

**Base:** everything rides Phase 12's rails — the `GooglePort` seam (all Google
traffic behind one injectable interface), `requireConnection('user', id)` +
`withGoogle(account, fn)`, the 409 `google_*` error contract, and the
`Caller.googleUserId` rule for agents. Migration numbering continues at
**0018**.

## Deviations from the master plan, decided up front

1. **In-app Drive picker instead of Google Picker JS.** The Picker needs an
   extra CDN script, a developer API key, and a client-side OAuth token. We
   already hold `drive.readonly` server-side, so the attach flow uses our own
   `/api/drive/files` browse/search in a dialog — self-contained, testable
   against the fake, no third credential. If drive.file-only scoping ever
   matters, the Picker can replace the dialog without touching the API.
2. **`share with domain` toggle deferred.** Modifying permissions needs a write
   scope beyond `drive.readonly`/`drive.file`. v1 ships the documented caveat
   instead (an attached file may still require requesting access in Google),
   which the master plan already treats as the baseline.

## OAuth scope change — affects existing connections

`USER_SCOPES` gains `drive.readonly` (browse/search/metadata) and `drive.file`
(upload into the bound folder). **Existing user connections lack these** and
Drive calls against an old grant return 403s from Google, not `invalid_grant` —
so `driveService` must map Google's `insufficient scopes` failure to the
existing `google_connection_broken`-style 409 (`google_drive_scope_missing`)
telling the user to reconnect. The connect button already forces
`prompt=consent`, so reconnecting is the whole fix.

## Global constraints

- All Google traffic stays behind `services/google/port.ts`; suites use the
  fake. No Drive types leak past `driveService`.
- Drive browsing/upload always uses the **acting user's own** connection —
  never a shared credential. A project folder binding stores ids, not tokens.
- **A gdrive attachment is a reference, not bytes**: `storage_key` NULL,
  `drive_file_id` set, exactly one of the two per row (CHECK constraint).
  The GC and object-deletion paths must skip provider='gdrive' rows — there is
  no object to delete, and deleting the Drive file would be wrong anyway.
- `GET /api/files/:id` stays internal-only; gdrive chips deep-link to
  `web_view_link`. The visibility rule (files inherit the parent's) applies to
  the *chip metadata* exactly as before.
- Fail-soft: no Google connection → project Files tab and My Drive render the
  Phase 12 connect prompt; attach-from-Drive is simply not offered.
- Commits small + conventional; `npm test` green per task.
